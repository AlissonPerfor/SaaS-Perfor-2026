# P0.2 — autenticação e sessão

Branch: `security/p0-2-auth-session`. PR: https://github.com/AlissonPerfor/SaaS-Perfor-2026/pull/1

## Revisão e verificações automatizadas

- Cliente Supabase exclusivo de cada `st.session_state`, sem cache global de Auth.
- `get_session()` renova o token quando necessário; `get_user(access_token)` valida o usuário no servidor a cada execução completa do app. Identidade local e remota devem coincidir.
- Logout usa `scope=local`, preservando outras sessões da mesma conta. Falhas remotas não impedem a limpeza local.
- Login novo ou malsucedido não herda cliente, projetos, relatórios ou navegação anteriores. Estado parcial ou inválido também é descartado.
- Renovação em segundo plano desativada para não manter timers de sessões desconectadas; a renovação ocorre no próximo `get_session()`.
- Python 3.12: 25 testes aprovados, incluindo SDK real com transporte HTTP simulado e Streamlit AppTest. Nenhuma credencial real utilizada nem e-mail enviado.
- Sintaxe compatível com Python 3.11 nos 18 arquivos da aplicação (não equivale a execução no Python 3.11).
- Ruff `E9,F63,F7,F82` aprovado para `main.py`, `core`, `modules` e testes. `pip check` e `git diff --check` aprovados.
- Streamlit 1.64.0 e Supabase 2.31.0 fixados em `requirements.txt`. `requirements-validation.lock` registra o ambiente completo de validação, incluindo ferramentas de teste, no Windows/Python 3.12; não é um lock multiplataforma de produção.

Para reproduzir em um ambiente virtual novo, fora da `.venv` já versionada no repositório:

```text
python -m pip install -r requirements-validation.lock
python -B -m pytest -q -p no:cacheprovider tests
python -B -m ruff check --select E9,F63,F7,F82 main.py core modules tests
python -m pip check
```

## Um único smoke test manual antes do merge

O ambiente local preparado nesta revisão atende em http://127.0.0.1:8502 enquanto o processo estiver ativo. Ele executa esta branch e referencia o arquivo de secrets existente, sem copiá-lo para o repositório. O endpoint de saúde do Auth respondeu HTTP 200; login real e credenciais dos dois usuários ficam para a validação manual.

Para reiniciar, a partir da cópia desta branch e com o ambiente de dependências ativado:

```text
python -X utf8 -B -m streamlit run main.py --server.address 127.0.0.1 --server.port 8502 --server.headless true --browser.gatherUsageStats false --secrets.files "CAMINHO_DO_SECRETS_EXISTENTE"
```

O teste adicional intercala duas sessões Streamlit com clientes reais do SDK e HTTP simulado, conferindo identidade, token, projetos, logout independente e troca A → B sem reaproveitar relatórios ou seleção de projeto.

Preparação: executar `main.py` a partir da branch do PR em um ambiente de teste com os secrets já configurados pelo responsável. Não trocar a branch do deploy de produção. Usar duas contas de teste A e B, com seus projetos esperados conhecidos. Abrir dois navegadores/perfis independentes (por exemplo, Chrome e Edge); duas janelas anônimas do mesmo navegador podem compartilhar contexto.

1. **Visitante e senha incorreta:** abrir o app nos dois navegadores. Ambos devem mostrar login. Tentar uma senha incorreta: erro controlado, sem acesso ao painel.
2. **Duas contas simultâneas:** entrar como A no primeiro e B no segundo. Conferir nome, perfil e projetos esperados; navegar entre projetos em ambos. Não deve haver troca de identidade nem resíduos de navegação da outra sessão.
3. **Logout e troca de conta:** sair de A, interagir com B e confirmar que B continua conectado. No primeiro navegador, entrar como B: projetos, seleção e relatórios antigos de A não devem reaparecer.
4. **Mesma conta em dois navegadores:** agora B está nos dois. Sair de um; no outro, navegar novamente e confirmar que continua conectado. Para confirmar também a renovação independente, manter a sessão restante até a expiração natural do access token e então navegar; ela deve renovar normalmente. Não alterar o TTL de produção para acelerar o teste.
5. **Recuperação de senha:** na tela de login, abrir “Esqueci minha senha”, informar o e-mail de uma conta de teste e enviar uma única vez. Conferir mensagem e recebimento do e-mail. Este lote preserva o envio existente; não implementa tela/callback de definição de nova senha.
6. **Saída final:** sair, atualizar a página e confirmar retorno ao login, sem conteúdo do usuário anterior.

Registrar em uma única resposta: commit testado, ambiente, aprovação/reprovação dos seis passos e qualquer erro observado. Não registrar senhas ou tokens. O smoke real ainda está pendente; os testes simulados não o substituem.

## Limites do lote

Sem alterações de RLS, esquema, permissões de negócio ou integrações. Nenhum merge/deploy realizado. Em indisponibilidade do Auth, a aplicação bloqueia o acesso e exige novo login. Não há promessa de revogação instantânea de JWT já emitido: o Supabase revoga refresh tokens no logout, e access tokens podem permanecer válidos até expirar. Recarregar/reconectar pode criar nova sessão Streamlit e exigir login novamente.

Referências conferidas: [get_user](https://supabase.com/docs/reference/python/auth-getuser), [get_session](https://supabase.com/docs/reference/python/auth-getsession), [sign_out](https://supabase.com/docs/reference/python/auth-signout). As assinaturas e a renovação também foram verificadas no SDK instalado e nos testes de compatibilidade.
